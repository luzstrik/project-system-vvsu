
# Лабораторная работа №7: Логическая модель БД

## Текстовое описание проектирования

**Контекст:** Мы проектируем БД для ИС спортивных организаций города (SportCity), которая учитывает спортивные сооружения, спортсменов, тренеров, клубы, соревнования и организаторов. Все требования берём из прошлых лабораторных работ (лаб. 1–6).

## Выделяем основные сущности

На основе анализа предметной области (лаб. 1), контекстной диаграммы DFD (лаб. 2) и функциональных требований (лаб. 5) выделяем следующие хранимые сущности:

| Сущность | Почему она нужна | Ссылка на требования |
|----------|------------------|----------------------|
| **Club** (Клуб) | Спортсмены состоят в клубах, у каждого клуба есть адрес и название | ФТ-СПР-02, ФТ-ОТЧ-09 |
| **Athlete** (Спортсмен) | Основная единица учёта, имеет разряд, дату рождения, привязку к клубу | ФТ-СПР-01, ФТ-ОТЧ-02 |
| **Coach** (Тренер) | Тренирует спортсменов, имеет квалификацию и специализацию | ФТ-ТРН-01, ФТ-ОТЧ-10 |
| **SportType** (Вид спорта) | Справочник дисциплин: футбол, плавание, бег и т.д. | ФТ-ОТЧ-02, ФТ-СОР-02 |
| **FacilityType** (Тип сооружения) | Определяет специфические атрибуты объектов (вместимость, покрытие) | ФТ-ОБЪ-02 |
| **Facility** (Сооружение) | Спортивные объекты: стадионы, корты, манежи | ФТ-ОБЪ-01, ФТ-ОТЧ-01 |
| **Organizer** (Организатор) | Проводит соревнования, может быть юрлицом или физлицом | ФТ-СОР-03, ФТ-ОТЧ-12 |
| **Competition** (Соревнование) | Ключевое событие: привязано к виду спорта, сооружению, организатору | ФТ-СОР-01, ФТ-ОТЧ-06 |
| **Participation** (Участие) | Факт выступления спортсмена на соревновании с результатом и местом | ФТ-УЧА-02, ФТ-ОТЧ-07 |
| **Award** (Награждение) | Медаль, грамота, разряд по итогам выступления | ФТ-УЧА-04 |
| **MedicalRecord** (Медосмотр) | Результаты медосмотров, срок действия справки | ФТ-МЕД-01, ФТ-МЕД-02 |

**Почему выделяем именно эти сущности?**
- Все они явно указаны в лаб. 1 как хранимые сущности
- Каждая имеет собственные атрибуты и жизненный цикл
- Они покрывают все 13 типовых запросов из лаб. 1
- Соответствуют бизнес-правилам предметной области

## Промежуточные (связующие) сущности

| Сущность | Зачем нужна | Тип связи |
|----------|-------------|-----------|
| **AthleteSport** | Реализует связь "спортсмен занимается несколькими видами спорта" | M:N (Athlete ↔ SportType) |
| **CoachAssignment** | Связывает тренера, спортсмена и вид спорта (с ролью тренера) | M:N с атрибутами (Coach ↔ Athlete ↔ SportType) |

### Почему нужны именно эти промежуточные таблицы?

1. **AthleteSport**: Согласно бизнес-правилу из лаб. 1 — *"один спортсмен может заниматься несколькими видами спорта"*. Прямая связь M:N невозможна в реляционной БД — нужна ассоциативная таблица. Дополнительно хранит дату присоединения к виду спорта.

2. **CoachAssignment**: Бизнес-правило: *"в рамках одного вида спорта спортсмен может тренироваться у нескольких тренеров"*. Это тройная связь (тренер-спортсмен-вид спорта), которую нельзя разбить на две бинарные без потери информации. Таблица также хранит роль тренера (основной, по ОФП, по технике).

### Почему НЕ нужны другие промежуточные таблицы?
- **Competition ↔ Facility / SportType / Organizer**: связь M:1 (одно соревнование = один вид спорта + одно сооружение + один организатор), реализуется через FK в таблице `Competition`.
- **Participation** уже является связующей таблицей между `Athlete` и `Competition` с собственными атрибутами (`result_value`, `place`).
- **Award** привязан к `Participation` (1:M), а не напрямую к `Athlete`.

## Атрибуты сущностей

### Club (Спортивный клуб)
```
id             : PK, UUID
name           : VARCHAR(255), NOT NULL, UNIQUE
address        : VARCHAR(512), NULLABLE
created_at     : TIMESTAMP, DEFAULT CURRENT_TIMESTAMP
```
**Обоснование:** UUID вместо AUTO_INCREMENT для безопасности и распределённых систем. UNIQUE на `name` предотвращает дублирование клубов.

### SportType (Вид спорта)
```
id       : PK, UUID
name     : VARCHAR(100), NOT NULL, UNIQUE
category : VARCHAR(100), NULLABLE  # игровой, единоборства, циклический...
```

### FacilityType (Тип сооружения)
```
id   : PK, UUID
name : VARCHAR(100), NOT NULL, UNIQUE  # стадион, корт, манеж, зал
```

### Facility (Спортивное сооружение)
```
id             : PK, UUID
type_id        : FK → FacilityType.id, NOT NULL
name           : VARCHAR(255), NOT NULL
address        : VARCHAR(512), NOT NULL
common_attrs   : JSON, NULLABLE        # общие: площадь, год ввода
specific_attrs : JSON, NULLABLE        # типозависимые: вместимость, покрытие
status         : ENUM('ACTIVE','MAINTENANCE','CLOSED'), DEFAULT 'ACTIVE'
```

**Почему JSON для `specific_attrs`?** Согласно лаб. 1: *"спортивные сооружения имеют специфические характеристики в зависимости от типа"*. Если бы мы создали колонки `capacity`, `surface_type`, `has_tribunes` в одной таблице, то для корта `capacity` был бы NULL, для стадиона `surface_type` — NULL. Это нарушение 3НФ (проблема sparse columns). JSON позволяет хранить разнородные атрибуты без денормализации.

### Organizer (Организатор)
```
id           : PK, UUID
name         : VARCHAR(255), NOT NULL  # название юрлица или ФИО физлица
contact_info : VARCHAR(255), NULLABLE
type         : ENUM('LEGAL','PERSON'), DEFAULT 'LEGAL'
```

### Athlete (Спортсмен)
```
id           : PK, UUID
first_name   : VARCHAR(100), NOT NULL
last_name    : VARCHAR(100), NOT NULL
birth_date   : DATE, NOT NULL
club_id      : FK → Club.id, NOT NULL
current_rank : VARCHAR(50), NULLABLE  # КМС, МС, 1 разряд...
```

**Ключевой момент:** `club_id NOT NULL` жёстко реализует правило из лаб. 1 — *"один спортсмен состоит только в одном клубе"*. Нельзя создать спортсмена без клуба.

### Coach (Тренер)
```
id             : PK, UUID
first_name     : VARCHAR(100), NOT NULL
last_name      : VARCHAR(100), NOT NULL
qualification  : VARCHAR(100), NULLABLE  # высшая, первая, без категории
specialization : VARCHAR(100), NULLABLE
```

### Competition (Соревнование)
```
id           : PK, UUID
name         : VARCHAR(255), NOT NULL
start_date   : DATE, NOT NULL
end_date     : DATE, NOT NULL
sport_id     : FK → SportType.id, NOT NULL
facility_id  : FK → Facility.id, NOT NULL
organizer_id : FK → Organizer.id, NOT NULL
status       : ENUM('PLANNED','ACTIVE','FINISHED','CANCELLED','POSTPONED'), DEFAULT 'PLANNED'
regulation   : TEXT, NULLABLE  # положение о соревновании
```

**Обоснование трёх FK:** Согласно лаб. 1: *"соревнование проводится по одному виду спорта, на одном сооружении, имеет одного организатора"*. Все три поля NOT NULL — соревнование не может существовать без этих привязок. CHECK: `end_date >= start_date`.

### Participation (Участие)
```
id              : PK, UUID
athlete_id      : FK → Athlete.id, NOT NULL
competition_id  : FK → Competition.id, NOT NULL
result_value    : VARCHAR(100), NULLABLE  # время, очки, баллы
place           : INT, NULLABLE
is_approved     : BOOLEAN, DEFAULT FALSE
```

**Почему это отдельная сущность, а не просто связь?** Потому что имеет собственные атрибуты (`result_value`, `place`, `is_approved`), которые функционально зависят от пары (спортсмен, соревнование). Это классическое приведение к 3НФ. UNIQUE constraint на `(athlete_id, competition_id)` предотвращает дублирование участия.

### Award (Награждение)
```
id               : PK, UUID
participation_id : FK → Participation.id, NOT NULL
award_type       : VARCHAR(100), NOT NULL  # медаль, грамота, разряд
issued_at        : DATE, DEFAULT CURRENT_DATE
```

**Почему привязка к `Participation`, а не к `Athlete`?** Согласно лаб. 1: *"по итогам соревнований спортсмены получают награды"*. Награда всегда привязана к конкретному выступлению, иначе теряется контекст.

### MedicalRecord (Медосмотр)
```
id           : PK, UUID
athlete_id   : FK → Athlete.id, NOT NULL
issue_date   : DATE, NOT NULL
expiry_date  : DATE, NOT NULL
conclusion   : TEXT, NULLABLE
doctor_name  : VARCHAR(255), NULLABLE
```

CHECK: `expiry_date > issue_date`. Реализует требование ФТ-МЕД-02 из лаб. 5 о проверке актуальности медсправки.

## Промежуточные таблицы M:N

### AthleteSport (спортсмен занимается видами спорта)
```
id         : PK, UUID
athlete_id : FK → Athlete.id, NOT NULL
sport_id   : FK → SportType.id, NOT NULL
joined_at  : DATE, DEFAULT CURRENT_DATE
```
UNIQUE: `(athlete_id, sport_id)` — спортсмен не может быть записан на один вид спорта дважды.

### CoachAssignment (тренер тренирует спортсмена по виду спорта)
```
id         : PK, UUID
coach_id   : FK → Coach.id, NOT NULL
athlete_id : FK → Athlete.id, NOT NULL
sport_id   : FK → SportType.id, NOT NULL
role       : VARCHAR(100), NULLABLE  # основной, по ОФП, по технике
```
UNIQUE: `(coach_id, athlete_id, sport_id)` — один тренер не может быть назначен одному спортсмену по одному виду спорта дважды.

## Ключевые моменты по связям

1. **Athlete → Club (M:1)**: Жёсткая связь через `club_id NOT NULL` в таблице Athlete. Реализует правило *"один спортсмен = один клуб"* из лаб. 1.

2. **Athlete ↔ SportType (M:N)**: Через промежуточную таблицу `AthleteSport`. Один спортсмен может заниматься несколькими видами спорта (баскетбол + лёгкая атлетика).

3. **Athlete ↔ Coach (M:N с контекстом)**: Через таблицу `CoachAssignment` с тройным ключом `(coach_id, athlete_id, sport_id)`. Один спортсмен в рамках одного вида спорта может тренироваться у нескольких тренеров.

4. **Competition → Facility / SportType / Organizer (M:1)**: Три FK в таблице Competition. Одно соревнование = один вид спорта + одно сооружение + один организатор.

5. **Participation (связующая сущность Athlete ↔ Competition)**: Нормализованная связь M:N с собственными атрибутами.

6. **Award → Participation (M:1)**: Награждение привязано к конкретному выступлению.

7. **FacilityType → Facility (1:M)**: Тип определяет структуру специфических атрибутов (хранятся в JSON).

## Ограничения целостности

### Первичные и внешние ключи

| Таблица | PK | Важные FK | Правило ON DELETE |
|---------|-----|-----------|-------------------|
| Athlete | id | club_id | RESTRICT (нельзя удалить клуб со спортсменами) |
| Competition | id | sport_id, facility_id, organizer_id | RESTRICT (нельзя удалить вид спорта/сооружение/организатора, если есть соревнования) |
| Participation | id | athlete_id, competition_id | RESTRICT для athlete (сохраняем историю), CASCADE для competition |
| Award | id | participation_id | CASCADE (если удалили участие — удаляем награды) |
| AthleteSport | id | athlete_id, sport_id | CASCADE для athlete, RESTRICT для sport |
| CoachAssignment | id | coach_id, athlete_id, sport_id | CASCADE для coach/athlete, RESTRICT для sport |
| MedicalRecord | id | athlete_id | CASCADE (если удалили спортсмена — удаляем медкарты) |

**Почему RESTRICT в критичных местах?** Чтобы защитить исторические данные. Нельзя удалить спортсмена, у которого есть история выступлений (`Participation`). Нельзя удалить стадион, если на него есть запланированные соревнования.

### Уникальность и обязательность
```sql
UNIQUE (club.name)                              -- название клуба уникально
UNIQUE (sport_type.name)                        -- вид спорта не дублируется
UNIQUE (facility_type.name)                     -- тип сооружения уникален
UNIQUE (athlete_id, competition_id) IN participation      -- одно участие на соревнование
UNIQUE (coach_id, athlete_id, sport_id) IN coach_assignment  -- уникальное назначение

NOT NULL (start_date, end_date)                 -- у соревнования обязательные даты
CHECK (end_date >= start_date)                  -- логика дат соревнования
CHECK (expiry_date > issue_date)                -- медсправка не может истечь раньше выдачи
CHECK (place > 0)                               -- место должно быть положительным
```

### Бизнес-правила на уровне БД
1. **Один спортсмен = один клуб**: Реализовано через `club_id NOT NULL` в таблице Athlete (не нужно создавать отдельную таблицу AthleteClub).
2. **Соревнование по одному виду спорта на одном сооружении**: Три NOT NULL FK в Competition.
3. **Награждение только за участие**: FK `participation_id` в Award без NULL.
4. **Медсправка не может быть бессрочной**: `expiry_date NOT NULL` + CHECK.

## Нормализация до 3НФ

### ✅ 1НФ: Все атрибуты атомарны
- Нет списков в одном поле (кроме осознанного решения с JSON для `specific_attrs` — это не нарушение 1НФ, а современный подход для полиморфных атрибутов).
- ФИО разбито на `first_name`, `last_name` (можно искать по фамилии).
- Адрес — атомарное поле (можно детализировать при необходимости).

### ✅ 2НФ: Все неключевые атрибуты зависят от полного первичного ключа
- В `Participation`: `result_value` и `place` зависят от пары `(athlete_id, competition_id)`, а не от одного из них.
- В `CoachAssignment`: `role` зависит от тройки `(coach_id, athlete_id, sport_id)`.
- В `AthleteSport`: `joined_at` зависит от пары `(athlete_id, sport_id)`.

### ✅ 3НФ: Нет транзитивных зависимостей
- Нет атрибутов, которые зависят от других неключевых полей.
- Например, если бы мы хранили `club_address` в таблице Athlete, это была бы транзитивная зависимость: `athlete → club → club_address`. Вместо этого мы используем FK `club_id` и JOIN при необходимости.

### Дополнительные меры нормализации:

1. **Вынесение специфических атрибутов сооружений в JSON**: Вместо создания кучи NULL-колонок (`capacity`, `surface_type`, `has_tribunes`) в таблице Facility, мы используем JSON-поле `specific_attrs`. Это не денормализация — это решение проблемы полиморфизма атрибутов без нарушения 3НФ.

2. **Separate MedicalRecord таблица**: Медосмотры вынесены в отдельную таблицу, а не встроены в Athlete, потому что у спортсмена может быть несколько медосмотров за историю (каждый год). Это связь 1:M, не 1:1.

3. **Participation как самостоятельная сущность**: Если бы мы хранили результат и место прямо в связи Athlete-Competition, это было бы нарушение 3НФ (атрибуты зависят от составного ключа). Вынос в отдельную таблицу с собственным PK — правильная нормализация.

4. **Award привязан к Participation, а не к Athlete**: Если бы награда была привязана напрямую к спортсмену, мы бы потеряли контекст (за какое соревнование). Это нарушение 3НФ — атрибут `award_type` зависел бы от `participation_id`, который не является ключом таблицы Athlete.
